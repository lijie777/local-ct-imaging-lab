# Feature Specification: 病人管理

**Feature Branch**: `001-patient-management`

**Created**: 2026-07-17

**Status**: Complete

**Input**: User description: "构建本地医疗 CT 教学应用的第一个可独立运行功能：病人管理。用户可以创建、查看、编辑、搜索和删除病人，数据在本机持久保存，当前阶段不包含任何 DICOM 或影像功能。"

## Clarifications

### Session 2026-07-17

- Q: “教学演示软件，不用于临床诊断”应在哪些位置显示？ → A: 病人管理页面和界面状态包括
  病人列表、空列表状态、搜索结果、搜索无结果状态、加载和操作失败状态、病人详情、创建病人的
  覆盖式界面、编辑病人的覆盖式界面和删除确认界面。病人列表、详情及其他完整页面顶部持续显示
  完整提示；覆盖式界面不得遮挡该提示，无法保持底层横幅清晰可见时，必须在覆盖式界面中重复
  显示完整提示。
- Q: 病历号内部空白与符号如何处理？ → A: 允许 1 至 64 个可见字符；去除首尾空白，
  保留内部空格和符号；唯一性比较不区分英文字母大小写。
- Q: 姓名、性别和出生日期采用哪组输入规则？ → A: 姓名为 1 至 100 个可见字符，去除首尾
  空白并保留内部空格及标点，拒绝控制字符；性别限定为男、女、其他、未知；出生日期为不晚于
  今天的任意有效日期。
- Q: 创建或编辑失败后，用户输入保留到什么范围？ → A: 校验失败或本地持久化失败后保持
  表单打开并保留全部输入；仅在保存成功或用户明确取消后清除；页面刷新或服务重启后无需恢复
  未提交草稿。
- Q: 最近更新时间相同时如何确定稳定排序？ → A: 先按最近更新时间降序；时间相同时按规范化
  后的病历号升序；完整列表和搜索结果使用同一排序规则。
- Q: 病人详情页必须显示哪些用户可见信息？ → A: 必须显示病历号、姓名、性别、出生日期、
  影像检查数量、最近检查日期、创建时间和最近更新时间；内部数据库 UUID 不属于用户可见字段，
  不在界面中显示。

## Constitutional Constraints *(mandatory)*

- **Safety notice**: 病人管理页面和界面状态包括病人列表、空列表状态、搜索结果、搜索无结果
  状态、加载和操作失败状态、病人详情、创建病人的覆盖式界面、编辑病人的覆盖式界面和删除
  确认界面。病人列表、详情及其他完整页面顶部必须持续、清晰地显示“教学演示软件，不用于
  临床诊断”。创建、编辑和删除确认等覆盖式界面不得遮挡该提示；如果无法保持底层横幅清晰
  可见，则必须在覆盖式界面中重复显示完整提示。该提示不得只在启动时或临时消息中显示。
- **Data boundary**: 本功能仅供一名本地用户离线使用。病人信息必须保留在本机，
  不得上传、同步、遥测或发送到外部服务，并且本地服务重启后仍可访问。
- **Scope boundary**: 本功能不得加入云服务、登录认证、PACS、DICOMweb、诊断报告、
  影像测量、三维体绘制、DICOM 导入、CT 查看器或其他影像处理能力。
- **DICOM lifecycle**: 本功能不接收、不索引也不删除 DICOM 文件。删除病人时只处理
  当前阶段存在的病人信息；DICOM 数据生命周期留给后续独立功能。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建并持久查看病人 (Priority: P1)

本地用户可以录入病历号、姓名以及可选的性别和出生日期，创建病人后立即在列表和详情中
查看其信息。没有影像检查的病人在列表中显示检查数量为 0，最近检查日期为空；重启本地
服务后，已经创建的病人仍然存在。病人列表、空列表状态和病人详情顶部持续显示非临床提示；
创建病人的覆盖式界面不得遮挡该提示，无法保持底层横幅清晰可见时必须重复显示完整提示。

**Why this priority**: 创建、查看和持久保存病人是所有后续管理及影像功能的基础，也是本功能
能够独立运行的最小价值闭环。

**Independent Test**: 从空数据开始创建一位病人，核对列表和创建界面的非临床提示，再核对
详情中的病历号、姓名、性别、出生日期、检查数量、最近检查日期、创建时间和最近更新时间，
确认不显示内部数据库 UUID；重启本地服务后再次打开同一病人，所有已保存内容应保持不变。

**Acceptance Scenarios**:

1. **Given** 当前没有病人，**When** 用户填写唯一病历号和姓名并提交，**Then** 系统创建病人，
   在列表中显示该病人的所有已填写字段、检查数量 0 和空的最近检查日期。
2. **Given** 已成功创建病人，**When** 用户打开病人详情，**Then** 系统显示病历号、姓名、性别、
   出生日期、检查数量、最近检查日期、创建时间和最近更新时间，不显示内部数据库 UUID，并保持
   教学演示限制可见。
3. **Given** 已成功创建病人，**When** 本地服务重启后用户重新打开病人列表，**Then** 该病人及其
   已保存字段仍然存在。
4. **Given** 已存在某个病历号，**When** 用户尝试用等价病历号创建另一位病人，**Then** 系统拒绝
   创建，并明确指出病历号重复。
5. **Given** 用户打开创建病人的覆盖式界面，**When** 该界面显示，**Then** 底层非临床提示保持
   清晰可见；如果无法保持，则覆盖式界面内重复显示完整提示。

---

### User Story 2 - 搜索并编辑病人 (Priority: P2)

本地用户可以按病历号或姓名搜索病人，打开匹配结果并修改病历号、姓名、性别或出生日期。
修改后的信息立即反映在列表和详情中，并在本地服务重启后保留。搜索结果、搜索无结果状态、
加载和操作失败状态必须保持完整页面顶部的非临床提示可见；编辑病人的覆盖式界面不得遮挡该
提示，无法保持底层横幅清晰可见时必须重复显示完整提示。

**Why this priority**: 病人信息会发生录入修正，用户必须能够快速找到目标并安全更新数据，
否则病人管理无法在持续使用中保持准确。

**Independent Test**: 预置多位病人，分别使用完整和部分病历号、姓名进行搜索，编辑其中一位
病人并重启本地服务，核对搜索范围、更新结果和持久性。

**Acceptance Scenarios**:

1. **Given** 存在多位病人，**When** 用户输入病历号或姓名的部分文本，**Then** 列表只显示病历号
   或姓名包含该文本的病人。
2. **Given** 搜索条件没有匹配病人，**When** 搜索完成，**Then** 系统显示明确的无结果状态，并允许
   用户清除搜索条件返回完整列表。
3. **Given** 用户正在编辑现有病人，**When** 提交合法且唯一的更新内容，**Then** 列表和详情显示
   更新后的字段，其他病人的信息保持不变。
4. **Given** 用户把病历号修改为另一位病人已使用的病历号，**When** 提交修改，**Then** 系统拒绝
   保存，指出病历号重复，并保留用户尚未成功提交的输入。
5. **Given** 编辑已成功保存，**When** 本地服务重启后再次搜索该病人，**Then** 更新后的内容仍然存在。
6. **Given** 用户处于搜索结果、搜索无结果、加载或操作失败状态，**When** 对应状态显示，**Then**
   完整页面顶部持续显示完整的非临床提示。
7. **Given** 用户打开编辑病人的覆盖式界面，**When** 该界面显示，**Then** 底层非临床提示保持
   清晰可见；如果无法保持，则覆盖式界面内重复显示完整提示。

---

### User Story 3 - 二次确认删除病人 (Priority: P3)

本地用户可以发起删除病人操作。系统必须先显示包含病人姓名和病历号的明确二次确认；用户
取消时不改变数据，用户确认时才删除病人，并且重启本地服务后该病人仍保持已删除状态。删除
确认界面不得遮挡非临床提示，无法保持底层横幅清晰可见时必须在确认界面内重复显示完整提示。

**Why this priority**: 删除是不可逆的破坏性操作，必须在完成基本创建和维护能力后提供，并通过
二次确认降低误删风险。

**Independent Test**: 对同一位预置病人先取消删除并确认其仍存在，再重新发起并确认删除，最后
重启本地服务并确认该病人不再出现。

**Acceptance Scenarios**:

1. **Given** 用户发起删除某位病人，**When** 二次确认出现，**Then** 确认内容显示该病人的姓名、
   病历号和删除后果，并同时提供取消与确认操作；底层非临床提示保持清晰可见，无法保持时在
   删除确认界面内重复显示完整提示。
2. **Given** 二次确认正在显示，**When** 用户选择取消，**Then** 对话关闭，病人记录保持不变。
3. **Given** 二次确认正在显示，**When** 用户明确确认删除，**Then** 系统删除病人，该病人从列表、
   搜索结果和详情入口中消失。
4. **Given** 病人已成功删除，**When** 本地服务重启后用户再次搜索，**Then** 该病人仍然不存在。
5. **Given** 删除无法保存，**When** 操作失败，**Then** 系统不得报告删除成功，病人记录保持可见，
   并显示可理解的失败原因。

### End-to-End Acceptance Path *(mandatory)*

1. 用户打开病人管理页，看到“教学演示软件，不用于临床诊断”和空列表状态。
2. 用户打开创建病人的覆盖式界面，确认非临床提示保持清晰可见或在覆盖式界面内重复显示；
   创建包含必填字段和可选字段的病人后，列表立即显示病人信息、检查数量 0 和空的最近检查日期。
3. 用户打开病人详情，核对八项用户可见信息、内部数据库 UUID 未显示以及教学演示限制。
4. 用户按姓名或病历号搜索该病人，核对搜索结果中的非临床提示；随后打开编辑覆盖式界面，
   确认提示保持清晰可见或重复显示，再修改姓名或可选字段并保存。
5. 用户重启本地服务并刷新浏览器，搜索到修改后的病人，确认数据持久存在。
6. 用户发起删除，确认删除界面不会遮挡非临床提示或已重复显示完整提示，再选择取消并确认
   病人仍然存在。
7. 用户再次发起删除并明确确认，确认病人从列表和搜索结果中消失。
8. 用户再次重启本地服务，确认被删除的病人没有恢复。

### Edge Cases

- 病历号或姓名为空、只包含空白、超过允许长度时，系统拒绝提交并指出具体字段和原因。
- 病历号去除首尾空白后与现有病历号仅有英文字母大小写差异时，视为重复。
- 病历号中的内部空格和符号必须原样保留；换行符和其他控制字符不是有效输入。
- 姓名包含中文、外文字母、内部空格或标点时，只要满足长度限制就可保存和搜索；换行符和
  其他控制字符不是有效输入。
- 性别未填写时按“未知”显示；出生日期未填写时显示为空。
- 出生日期不是有效日期或晚于当前日期时，系统拒绝提交并指出出生日期无效；有效历史日期
  不受任意最早日期限制。
- 搜索文本为空或清除后，系统恢复显示完整病人列表。
- 新建或编辑校验失败或持久化失败时，系统不得显示成功状态，必须保持表单打开并保留全部输入
  以便重试；只有保存成功或用户明确取消后才清除输入。
- 页面刷新或本地服务重启后无需恢复尚未提交的创建或编辑草稿。
- 删除持久化失败时，病人记录不得从本地数据中消失，也不得显示删除成功。
- 当前阶段不存在影像检查数据；任何病人的检查数量均为 0，最近检查日期均为空。
- 病人列表、空列表状态、搜索结果、搜索无结果状态、加载和操作失败状态以及病人详情等完整
  页面顶部必须持续显示完整的非临床提示。
- 创建、编辑或删除确认等覆盖式界面不得遮挡非临床提示；无法保持底层横幅清晰可见时，必须
  在覆盖式界面内重复显示完整提示。
- 病人详情必须显示病历号、姓名、性别、出生日期、影像检查数量、最近检查日期、创建时间和
  最近更新时间；即使内部数据库使用 UUID，也不得把 UUID 作为用户可见字段显示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许单个本地用户在浏览器中访问病人管理功能，且无需登录。
- **FR-002**: 病人管理页面和界面状态 MUST 包括病人列表、空列表状态、搜索结果、搜索无结果
  状态、加载和操作失败状态、病人详情、创建病人的覆盖式界面、编辑病人的覆盖式界面和删除
  确认界面。病人列表、详情及其他完整页面顶部 MUST 持续、清晰地显示“教学演示软件，不用于
  临床诊断”。创建、编辑和删除确认等覆盖式界面 MUST NOT 遮挡该提示；无法保持底层横幅清晰
  可见时，覆盖式界面内 MUST 重复显示完整提示。
- **FR-003**: 系统 MUST 允许用户使用病历号、姓名、可选性别和可选出生日期创建病人。
- **FR-004**: 病历号 MUST 去除首尾空白后为 1 至 64 个可见字符，内部空格和符号 MUST
  原样保留，换行符及其他控制字符 MUST 被拒绝。病历号 MUST 在所有病人中保持唯一，
  英文字母大小写差异不得绕过唯一性校验。
- **FR-005**: 姓名 MUST 去除首尾空白后为 1 至 100 个可见字符，内部空格和标点 MUST
  原样保留，换行符及其他控制字符 MUST 被拒绝。
- **FR-006**: 性别 MUST 为可选字段；未填写时按“未知”处理。允许值为男、女、其他和未知。
- **FR-007**: 出生日期 MUST 为可选的有效日期，并且不得晚于当前日期；不得设置任意最早日期
  限制，未填写时显示为空。
- **FR-008**: 输入校验失败时，系统 MUST 标识具体字段、说明失败原因、保持表单打开并保留
  全部输入；只有保存成功或用户明确取消后才能清除输入。
- **FR-009**: 系统 MUST 将成功创建或编辑的病人信息保存在本机，并在本地服务重启后恢复。
- **FR-010**: 病人列表 MUST 显示病历号、姓名、性别、出生日期、影像检查数量和最近检查日期。
- **FR-011**: 在当前功能阶段，系统 MUST 为每位病人显示影像检查数量 0 和空的最近检查日期。
- **FR-012**: 系统 MUST 提供病人详情，并显示病历号、姓名、性别、出生日期、影像检查数量、
  最近检查日期、创建时间和最近更新时间。内部数据库 UUID MUST NOT 作为用户可见字段显示。
- **FR-013**: 系统 MUST 允许用户编辑病历号、姓名、性别和出生日期，并对编辑后的值执行与
  创建时相同的校验和唯一性规则。
- **FR-014**: 系统 MUST 支持按病历号或姓名进行不区分英文字母大小写的子串搜索，并忽略
  搜索文本首尾空白。
- **FR-015**: 搜索没有匹配项时，系统 MUST 显示明确的无结果状态；清除搜索文本后 MUST
  恢复完整列表。
- **FR-016**: 完整病人列表和搜索结果 MUST 先按最近更新时间降序排列；最近更新时间相同时，
  MUST 按去除首尾空白且不区分英文字母大小写的病历号升序排列。
- **FR-017**: 删除病人前，系统 MUST 显示包含病人姓名、病历号和删除后果的二次确认。
- **FR-018**: 取消删除 MUST 保持病人信息不变；明确确认后，系统 MUST 删除病人并在重启后
  保持删除结果。
- **FR-019**: 创建、编辑或删除无法持久保存时，系统 MUST 显示失败原因，不得报告成功，也不得
  留下与用户所见状态不一致的本地记录。创建或编辑持久化失败时 MUST 保持表单打开并保留全部
  输入；未提交草稿无需在页面刷新或本地服务重启后恢复。
- **FR-020**: 系统 MUST 在没有病人时显示明确的空列表状态和创建病人的入口。
- **FR-021**: 病人信息 MUST 只保留在本机，不得上传、同步、遥测或发送到任何外部服务。

### Non-Goals *(mandatory)*

- 不导入、解析、索引、显示或删除 DICOM 文件。
- 不创建真实的影像检查、序列或实例数据。
- 不实现 CT 轴位查看器、三视图 MPR、影像工具、影像测量或三维体绘制。
- 不集成 PACS、DICOMweb、HIS、RIS 或其他外部医疗系统。
- 不实现登录、账户、角色、权限或多用户并发。
- 不提供云服务、远程访问、数据同步、遥测或外部备份。
- 不生成诊断报告，也不得支持临床诊断或治疗决策。

### Key Entities *(include if feature involves data)*

- **Patient（病人）**: 代表本地管理的一位病人，包含唯一病历号、姓名、可选性别、可选出生日期、
  创建时间和最近更新时间。当前阶段其影像检查数量固定为 0，最近检查日期为空。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 验收人员能够在一次连续浏览器流程中完成创建、查看、搜索、编辑和删除病人，
  所有步骤均得到与验收场景一致的结果。
- **SC-002**: 对有效、必填字段为空、重复病历号和非法出生日期的验收样例，100% 的提交结果
  正确，所有失败消息均指出具体字段和原因。
- **SC-003**: 本地服务重启后，100% 已确认创建和编辑的病人记录保持不变，100% 已确认删除的
  病人记录不会恢复。
- **SC-004**: 100% 的病人详情显示病历号、姓名、性别、出生日期、影像检查数量、最近检查日期、
  创建时间和最近更新时间，且不显示内部数据库 UUID；100% 没有影像检查的病人在列表和详情中
  显示检查数量 0、最近检查日期为空。
- **SC-005**: 100% 的病人列表、空列表状态、搜索结果、搜索无结果状态、加载和操作失败状态及
  病人详情等完整页面顶部持续显示“教学演示软件，不用于临床诊断”；100% 的创建、编辑和删除
  确认等覆盖式界面均不遮挡该提示，无法保持底层横幅清晰可见时均重复显示完整提示。
- **SC-006**: 在验收过程中，完成全部病人管理操作不需要登录、外网连接或任何外部服务。
- **SC-007**: 用户取消删除后病人数据保持不变；只有明确确认的删除才会永久移除病人。
- **SC-008**: 100% 的创建或编辑校验失败及持久化失败场景保持表单打开并保留全部输入；
  保存成功或用户明确取消后才清除输入。
- **SC-009**: 对相同病人数据，完整列表和搜索结果在页面刷新及本地服务重启后保持相同的
  确定排序顺序。

## Assumptions

- 本功能由一名本地用户离线使用，不考虑并发编辑、账户隔离或权限控制。
- 病历号仅去除首尾空白，内部空格和符号原样保留，并以不区分英文字母大小写的方式判断唯一性。
- 搜索对病历号和姓名执行不区分英文字母大小写的子串匹配；空搜索显示全部病人。
- 性别使用男、女、其他、未知四个展示值，未填写视为未知。
- 姓名仅去除首尾空白，内部空格和标点原样保留；换行符和其他控制字符不属于有效姓名。
- 出生日期可以是任何不晚于当前日期的有效日期，不设置任意最早日期。
- 完整病人列表和搜索结果先按最近更新时间降序排序；时间相同时按规范化病历号升序排序。
- 病人记录会保留到用户明确确认删除为止；第一版不提供回收站或撤销删除。
- 未提交的创建或编辑内容只在当前打开表单中保留，不作为可跨页面刷新或服务重启恢复的草稿。
- 当前阶段没有任何影像检查数据，因此检查数量和最近检查日期只是只读的空状态摘要。
- 本功能不依赖任何外部系统、在线服务或尚未实现的 DICOM 功能。
