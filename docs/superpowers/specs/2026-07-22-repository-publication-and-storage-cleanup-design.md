# 项目发布与删除残留自动清理设计

## 1. 背景

当前项目已经完成病人管理、DICOM 导入与持久化、轴位 CT 查看器和联动三视图 MPR，但根目录尚无 `README.md`，本地 Git 仓库没有提交历史和远端仓库。代码审查还确认了一项运行维护边界：病人数据库删除提交后，如果 `.delete-staging` 中的受管 DICOM 文件只清理了一部分便失败，数据库会保持正确的删除状态，但隔离目录中的剩余文件目前只能人工重试清理。

本次工作补齐启动时自动清理、项目级 README、最新验收记录和 GitHub 首次发布，不处理既有 Starlette、Cornerstone 构建或 WebGL context-limit 等非阻断技术债。

## 2. 目标与成功标准

- 后端每次启动时自动重试清理 `.delete-staging` 中的残留目录。
- 一个残留项清理失败时记录 warning，继续处理其他残留项，并允许本机服务启动。
- 自动清理只操作配置的 `.delete-staging` 根目录内部，不访问受管目录外路径。
- 根目录 `README.md` 能让新用户理解项目背景、目的、边界、架构、功能和启动方式。
- README 提供可直接执行的 Windows PowerShell 后端、前端、迁移、测试与构建命令。
- `004-three-view-mpr/quickstart.md` 保留原始验收记录，并追加本次修改后的最新回归结果。
- 全量后端测试、前端测试和 production build 通过后，才进入 Git 提交确认。
- 经最终确认后，将本地分支调整为 `main`，创建私有仓库 `lijie777/TestProj` 并推送首次提交。

## 3. 删除残留自动清理

### 3.1 清理时机

使用 FastAPI lifespan 在应用启动阶段调用 `ManagedStorage` 的待清理目录扫描方法。模块导入或单纯调用 `create_app()` 不删除文件；只有应用真正进入 lifespan 时才执行清理。

### 3.2 清理范围

清理方法只枚举 `delete_staging_dir` 的直接子项，并在删除前使用现有路径包含性校验确认目标仍位于该目录内部。目录不存在时视为没有待清理项，不主动创建空目录。

正常情况下暂存项是 `stage_patient_delete()` 创建的目录。为避免误删配置目录外数据，符号链接、路径逃逸或无法安全解析的子项必须拒绝并记为失败。

### 3.3 失败策略

每个残留项独立清理：成功项删除，失败项保留并记录不包含患者信息、绝对 DICOM 文件路径或内部堆栈的 warning。一次失败不阻止其他项清理，也不阻止服务启动；下一次启动会再次尝试。

清理结果不恢复数据库记录，也不把隔离目录移回正式 DICOM 目录，继续保持“可访问数据库不引用已删除文件”的一致性边界。

### 3.4 测试

- 空或不存在的 staging 根目录启动成功且无文件变更。
- 启动时清除一个完整残留目录。
- 第一个残留目录模拟清理失败后仍继续删除第二个目录，并保留失败目录。
- 路径校验拒绝越界目标。
- 既有病人删除、导入和应用启动测试无回归。

6. 环境要求：Windows PowerShell、Python 3.12、Node.js/npm，以及浏览器要求。
7. 快速启动：创建后端虚拟环境、安装依赖、执行 Alembic、启动 Uvicorn、安装前端依赖、启动 Vite。
8. 使用流程：创建病人、导入脱敏 CT、打开轴位查看器、进入 MPR。
9. 测试与 production build 命令。
10. 数据目录、删除行为、自动清理和隐私边界。

README 不加入徽章、宣传性截图、贡献者流程、许可证声明或部署到公网的说明，因为当前项目没有这些已确认内容。

## 6. Git 与 GitHub 发布

实现和验证完成后先重新核对工作区、忽略规则、敏感文件、当前分支及待提交文件。提交范围预计为整个项目源码、规格、设计、测试、README 和 `.gitignore`；虚拟环境、`node_modules`、数据库、DICOM、临时导入、删除 staging、日志和本地 IDE 文件必须保持排除。

计划将初始分支命名为 `main`，创建私有仓库 `lijie777/TestProj`，并使用一次初始功能提交发布当前完整项目。实际 `git add`、`git commit`、分支调整、仓库创建和 `git push` 必须在实施完成后重新列出准确范围、提交信息和步骤，取得用户最终确认后执行。

## 8. 风险与取舍

- 启动时尽力清理意味着被系统锁定的文件可能继续保留到下一次启动，但不会阻止应用使用，也不会恢复悬空数据库记录。
- 自动删除只针对内部 staging 根目录；路径安全校验优先于“尽可能删除”。
- README 命令将以当前 Windows 环境和项目实际配置为准，不承诺未经验证的 Linux/macOS 流程。
- 首次提交包含项目现有全部源码和规格，因此最终暂存前必须进行敏感信息和大文件检查。
